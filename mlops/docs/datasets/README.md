# Datasets

Every dataset used, why it was chosen, and what is wrong with it. The caveats matter more than
the row counts: most of them change how the pipeline has to be built.

**No raw data is committed to this repository.** Data is versioned by DVC against a private Azure
Blob remote, because several of these datasets carry competition terms restricting
redistribution. Contributors download from the original source and `dvc add` locally.

---

## Tier 1 — the platform is built on these

### Credit Risk · Home Credit Default Risk

- **Source:** [Kaggle — Home Credit Default Risk](https://www.kaggle.com/competitions/home-credit-default-risk)
- **Scale:** ~307k applications; 7 related tables; roughly 2.5 GB uncompressed
- **Target:** `TARGET` — client had payment difficulties on the loan

**Why this is the primary dataset.** It is the only one here with genuine relational structure
and semantically meaningful columns. `bureau`, `bureau_balance`, `previous_application`,
`POS_CASH_balance`, `instalments_payments` and `credit_card_balance` all require real joins and
aggregations over customer history — which is exactly the work a feature pipeline exists to do,
and exactly where point-in-time errors hide.

**Caveats:**

- **Point-in-time hazard, high.** The history tables are keyed by customer, not by application
  date. A naive `GROUP BY SK_ID_CURR` pulls in records that postdate the application and leaks
  the outcome. Every aggregation must take an explicit as-of timestamp — see
  [ADR-0004](../decisions/0004-temporal-validation.md).
- **Timestamps are relative.** `DAYS_BIRTH`, `DAYS_EMPLOYED` and similar are negative day offsets
  from the application, not absolute dates. A synthetic application-date axis is constructed so
  that chronological splitting is possible, and that construction is documented in the config.
- **`DAYS_EMPLOYED` contains a sentinel** (`365243`) standing in for "not employed". It must be
  handled explicitly; left alone it distorts binning and scaling badly.
- **Class imbalance:** roughly 8% positive. Mild by the standards of this project.
- **Licensing:** Kaggle competition rules. Redistribution is restricted — private DVC remote only.

### Fraud Detection · Sparkov synthetic credit-card transactions

- **Source:** [Kaggle — Fraud Detection (Sparkov generator)](https://www.kaggle.com/datasets/kartik2112/fraud-detection)
- **Scale:** ~1.85M transactions, ~1.3M train / ~0.55M test
- **Target:** `is_fraud`

**Why this over IEEE-CIS.** It has **real timestamps, merchant identity, merchant category,
transaction amount, and customer and merchant coordinates**. That makes real feature engineering
possible and defensible: transaction velocity over rolling windows, time since the customer's
last transaction, geographic distance from the customer's usual pattern, deviation from a
category-typical amount, hour-of-day and day-of-week effects.

None of that can be built on anonymized columns. Since feature engineering and point-in-time
correctness are central claims of this platform, the dataset has to support them.

**Caveats:**

- **Synthetic.** Generated by the Sparkov simulator. The fraud patterns are simpler and cleaner
  than real fraud, so metrics will look better than production reality. The engineering is
  transferable; the numbers are not.
- **Class imbalance:** roughly 0.5% positive.
- Provided with a pre-existing train/test split which is **not** used as given — splits are
  recomputed chronologically with a gap window.

## Tier 2 — CI fixtures

These exist so the full pipeline can execute in CI in seconds. They are teaching datasets and are
not presented as production banking models.

### Customer Churn · Bank Customer Churn

- **Source:** [Kaggle](https://www.kaggle.com/datasets/shubhammeshram579/bank-customer-churn-prediction)
- **Scale:** ~10k rows, ~10 features
- **Role:** primary smoke-test fixture

Small, clean, entirely tabular, and it runs end-to-end in seconds. **It has no time dimension at
all**, so it cannot exercise the temporal logic — an artificial timestamp column is generated for
fixture purposes only, and that fact is recorded in its config so nobody later mistakes it for a
temporal validation case.

### Marketing · Bank Marketing (UCI)

- **Source:** [UCI Machine Learning Repository](https://archive.ics.uci.edu/dataset/222/bank+marketing)
- **Scale:** ~45k campaign contacts
- **Role:** second fixture, different schema shape

Heavily categorical, which exercises a different branch of the encoding path than Churn does.
Contains `duration`, a **known leaking feature** — call duration is not knowable before the call
is made. It is dropped, and the drop is a deliberate test case for the leakage machinery. The
UCI licence permits redistribution, unlike the Kaggle competition datasets.

## Tier 3 — planned

### Anti-Money Laundering · IBM Transactions for AML

- **Source:** [Kaggle](https://www.kaggle.com/datasets/ealtman2019/ibm-transactions-for-anti-money-laundering-aml) · [IBM/AML-Data](https://github.com/IBM/AML-Data)
- **Variant to use:** `HI-Small` only
- **Target:** `Is Laundering`

Synthetic, generated by a multi-agent simulation — no real individuals are obfuscated in it.
Published in six variants (`HI`/`LI` × `Small`/`Medium`/`Large`), where `HI` denotes a higher
illicit ratio. The larger variants run to hundreds of millions of transactions and tens of
gigabytes, which is unworkable on a laptop and expensive in cloud storage. **Only `HI-Small` is
in scope**, and only after Phase 6.

**Caveats:**

- **Extreme imbalance** — laundering transactions are a very small fraction of a percent even in
  the `HI` variants. This breaks the evaluation approach used elsewhere: PR-AUC becomes unstable
  and threshold selection has to be driven almost entirely by alert budget.
- **Supervised classification is a simplification, and the README says so.** Production AML is
  rules engines plus anomaly detection plus network analysis. Labels come from SAR filings, which
  are rare, lagged, and biased toward what existing rules already flag — so a supervised model
  trained on them largely learns to imitate the incumbent rules.
- The data is naturally a **transaction graph**. Graph features are the interesting direction and
  are noted in the roadmap under *Later*.

## Considered and rejected

### IEEE-CIS Fraud Detection

- [Kaggle competition](https://www.kaggle.com/competitions/ieee-fraud-detection) · ~590k
  transactions, 434 columns

The best-known fraud dataset, and rejected deliberately.

- **The features are anonymized.** `V1`–`V339` plus the `C`, `D` and `M` families have no
  published meaning. A model can be trained on them; a *feature pipeline* cannot be demonstrated
  on them, because there is no semantics to engineer against and no way to defend a derived
  feature to a reviewer.
- **`TransactionDT` is a time delta**, not a timestamp — seconds from an undisclosed reference
  point. Chronological ordering works; calendar features and genuine recency windows do not.
- **Heavy missingness** across the identity tables, which dominates the engineering effort with
  imputation strategy rather than feature design.
- **Redistribution is restricted** by competition rules.

It remains a good candidate for a later *modelling* exercise — high-cardinality categoricals and
missingness at scale are real problems. It is a poor foundation for a platform whose main claim
is point-in-time-correct feature engineering.

### PaySim

Mobile money simulator, widely used, ~6.3M transactions. Rejected: only five transaction types
and a small, simple feature space, so the fraud pattern is close to trivially separable and the
engineering story is thin.

### Lending Club

Genuinely attractive for credit risk — real loans, real issue dates, real outcomes, a true
temporal axis, and a natural label-maturity problem. Kept as a **strong future alternative** to
Home Credit. Not chosen now because its relational structure is flatter, so it exercises the
aggregation and point-in-time machinery less, and its distribution history has been unstable
across mirrors.
