# Credentials, rotation, and rebuilding k8s-01

Where every credential the k3s workloads depend on lives, how to rotate each one without
downtime, and how to rebuild `k8s-01` from nothing. Everything else on the cluster comes back from
Git through Argo CD ([ADR-0007](../decisions/0007-argocd-gitops-on-k3s.md)); the credentials are
the part Git deliberately does not hold.

## Handling rules

These apply to every command below.

- **Never print a value**, not even through a filter meant to redact it. To check a value, compare
  the first 8 characters of its sha256, computed where it lives:
  `... | tr -d '\n' | shasum -a 256 | cut -c1-8` (`sha256sum` on the VMs).
- **List Secret keys by name only**:
  `sudo k3s kubectl -n NS get secret NAME -o go-template='{{range $k,$v := .data}}{{$k}} {{end}}'`.
- **Move values machine to machine on stdin**, from the command that produces them to the one
  that stores them. Values typed by hand go through `read -s`.
- **Run `ssh` on its own**, then paste the remote commands once the remote prompt is showing.
  Lines pasted together with `ssh` are not sent to the remote shell; they run on the Mac after it
  exits.
- Files holding a credential are mode `600`.

## Inventory

| Credential | Where it is stored | Where it comes from |
| --- | --- | --- |
| `bankmldvcstore` account key | Key Vault `bankml-kv`, secret `azure-storage-connection-string` (read by the Container App); k3s `bankml/azure-storage`; on `docker-01`, `infrastructure/homelab/mlflow/.env`, `mlops/.env` and `mlops/.dvc/config.local`; on the Mac, `mlops/.dvc/config.local` | Azure, `az storage account keys list -g bankml-data-rg -n bankmldvcstore` |
| Backup SAS token | `docker-01` `infrastructure/homelab/mlflow/.env`, `BACKUP_SAS_TOKEN` | Generated from the account key against the stored access policy `backup-writer` ([MLflow README](../../infrastructure/homelab/mlflow/README.md)) |
| BankML API keys | Container App secret `bankml-api-keys` (all pairs); k3s `bankml/bankml-api-key` (the `replay` key); `monitoring-01` `infrastructure/homelab/monitoring/secrets/bankml-api-key` (the `prometheus` key) | Generated, `openssl rand -hex 32` ([mlops ADR-0017](../../mlops/docs/decisions/0017-per-client-api-keys.md)) |
| Tailscale OAuth client | k3s `nexus/tailscale-oauth` | Tailscale admin console, Settings, Trust credentials, scope `devices:core:read` only |
| Grafana service account token | k3s `nexus/grafana-token` | Grafana, Administration, Users and access, Service accounts, the Nexus account (Viewer) |
| Argo CD admin password and session key | k3s `argocd/argocd-secret` | Generated by Argo CD; the password is set in its UI |

Not covered here: the MLflow Postgres password, the Cloudflare Tunnel and Access tokens, the
Discord webhook URLs, the Proxmox API token for Terraform, and the GitHub Actions secrets. Each is
documented with the component that uses it.

## Rotating the storage account key

The account has two keys, and consumers use one of them. Rotation moves every consumer to the
other key, checks each one, and only then regenerates the key being retired. Nothing breaks in
between, because both keys stay valid until the last step. The SAS token for backups is signed
with the account key, so it is regenerated in the same pass and the old one dies with the retired
key.

From the Mac, with `az login` done. Set `NEW` to the key being moved to:

```bash
NEW=key2   # or key1, whichever is not the one being retired
CS() { az storage account show-connection-string -g bankml-data-rg -n bankmldvcstore --key $NEW --query connectionString -o tsv; }
KEY() { az storage account keys list -g bankml-data-rg -n bankmldvcstore --query "[?keyName=='$NEW'].value" -o tsv; }
SSH="ssh -i $HOME/.ssh/id_ed25519_ai_lab"
```

1. The Container App, through Key Vault. The app reads Key Vault references when a revision
   starts, so the active revision is restarted:

   ```bash
   CS | tr -d '\n' > /tmp/cs && chmod 600 /tmp/cs
   az keyvault secret set --vault-name bankml-kv -n azure-storage-connection-string --file /tmp/cs --encoding utf-8 -o none
   rm /tmp/cs
   REV="$(az containerapp revision list -g bankml-rg -n bankml-credit-serving --query "[?properties.active].name | [0]" -o tsv)"
   az containerapp revision restart -g bankml-rg -n bankml-credit-serving --revision "$REV" -o none
   ```

2. The k3s Secret:

   ```bash
   CS | tr -d '\n' | $SSH ops@192.168.1.183 'sudo k3s kubectl -n bankml create secret generic azure-storage --from-file=AZURE_STORAGE_CONNECTION_STRING=/dev/stdin --dry-run=client -o yaml | sudo k3s kubectl apply -f -'
   ```

3. The two dotenv files on `docker-01`. Each replaces one line and keeps the file at `600`:

   ```bash
   for f in infrastructure/homelab/mlflow/.env mlops/.env; do
     CS | $SSH ops@192.168.1.115 "cd ~/ai-infrastructure-lab && read -r v && grep -v '^AZURE_STORAGE_CONNECTION_STRING=' $f > $f.new && printf 'AZURE_STORAGE_CONNECTION_STRING=%s\n' \"\$v\" >> $f.new && chmod 600 $f.new && mv $f.new $f && echo '$f updated'"
   done
   ```

4. The backup SAS token, signed with the new key:

   ```bash
   az storage container generate-sas --account-name bankmldvcstore --name backups \
     --policy-name backup-writer --https-only --account-key "$(KEY)" -o tsv \
   | $SSH ops@192.168.1.115 'cd ~/ai-infrastructure-lab/infrastructure/homelab/mlflow && read -r t && grep -v "^BACKUP_SAS_TOKEN=" .env > .env.new && printf "BACKUP_SAS_TOKEN=%s\n" "$t" >> .env.new && chmod 600 .env.new && mv .env.new .env && echo "SAS updated"'
   ```

5. The DVC remote, on `docker-01` and on the Mac:

   ```bash
   KEY | $SSH ops@192.168.1.115 'cd ~/ai-infrastructure-lab/mlops && read -r k && uv run dvc remote modify --local azremote account_key "$k" && chmod 600 .dvc/config.local && echo "dvc updated"'
   (cd mlops && KEY | { read -r k; uv run dvc remote modify --local azremote account_key "$k"; } && chmod 600 .dvc/config.local)
   ```

6. Restart MLflow so it reads the new connection string:

   ```bash
   $SSH ops@192.168.1.115 'cd ~/ai-infrastructure-lab/infrastructure/homelab/mlflow && docker compose up -d mlflow'
   ```

7. Check every consumer before retiring anything:

   - **Hashes.** Every location from the inventory shows the same 8 characters as `KEY | tr -d '\n' | shasum -a 256 | cut -c1-8`.
   - **MLflow.** Read the production model's `MLmodel` through `http://localhost:5000/api/2.0/mlflow-artifacts/artifacts/...` on `docker-01`.
   - **Backup.** On `docker-01`, `sudo systemctl start mlflow-backup.service` and see an upload in `journalctl -u mlflow-backup.service -n 5`.
   - **k3s.** `sudo k3s kubectl -n bankml create job drift-check --from=cronjob/drift-credit` completes. Delete it afterwards.
   - **DVC.** `uv run dvc status -c` in `mlops/` says the cache and remote are in sync.
   - **Container App.** After the next prediction, today's `credit/YYYY-MM-DD.jsonl` in the `predictions` container has a new modification time.

8. Retire the old key:

   ```bash
   az storage account keys renew -g bankml-data-rg -n bankmldvcstore --key key1 -o none   # the one being retired
   ```

## Rotating a BankML API key

Replace one `name:key` pair in the Container App secret, keep the others, and update the one
place that client reads its key from. The old key stops working when the revision restarts.

- `replay`: k3s `bankml/bankml-api-key`, same pattern as the storage Secret above.
- `prometheus`: `monitoring-01`'s `secrets/bankml-api-key`, owned by uid `65534`, mode `400`
  ([monitoring README](../../infrastructure/homelab/monitoring/README.md)).

Check: the new key gets `200` from `/metrics`, and the old one gets `401`.

## Rotating the Tailscale OAuth client and the Grafana token

Both are created in a web console, so the new value is typed on `k8s-01` with `read -s`.

1. Create the new one first, and keep the old one for now:
   - **Tailscale:** a new OAuth client with `devices:core:read` only. Its description names
     where it is used and the date.
   - **Grafana:** a new token on the Nexus service account.
2. On `k8s-01`. Each `read -s` waits silently for one value and Enter:

   ```bash
   read -s TS_ID; read -s TS_SECRET; read -s GRAFANA_TOKEN
   sudo k3s kubectl -n nexus create secret generic tailscale-oauth --from-literal=TS_OAUTH_CLIENT_ID="$TS_ID" --from-literal=TS_OAUTH_CLIENT_SECRET="$TS_SECRET" --dry-run=client -o yaml | sudo k3s kubectl apply -f -
   sudo k3s kubectl -n nexus create secret generic grafana-token --from-literal=GRAFANA_TOKEN="$GRAFANA_TOKEN" --dry-run=client -o yaml | sudo k3s kubectl apply -f -
   unset TS_ID TS_SECRET GRAFANA_TOKEN
   sudo k3s kubectl -n nexus rollout restart deploy/backend
   ```

3. Check that the values have the expected shape without printing them. The Tailscale secret
   starts with `tskey-client-`, and the Grafana token with `glsa_`. Then check that
   `curl -s localhost/api/topology` on `k8s-01` shows tailnet devices online, and that
   `curl -s localhost/api/alerts` has `"error": null`.
4. Revoke the old ones in the two consoles. Restart the backend again and repeat the check. A
   failure now means something was still using the old credential.

## Rotating the Argo CD session key

Signs UI and CLI sessions. Removing it makes Argo CD generate a new one and ends every session:

```bash
sudo k3s kubectl -n argocd patch secret argocd-secret --type=json -p='[{"op":"remove","path":"/data/server.secretkey"}]'
sudo k3s kubectl -n argocd rollout restart deploy/argocd-server
```

The admin password is changed in the UI, under User Info.

## Rebuilding k8s-01

For when the VM is lost or replaced. Order matters: the Secrets have to exist before Argo CD
syncs the workloads that read them, or those pods start and fail until they do.

1. **The VM.** Run `terraform apply` in `infrastructure/homelab/`
   ([README](../../infrastructure/homelab/README.md)). It creates `k8s-01` (VM 8001) if it is
   missing. Its address comes from DHCP. If it is no longer `192.168.1.183`, update the three
   `k8s-01` targets in `infrastructure/homelab/monitoring/prometheus.yml` (`node-k8s-01`,
   `kube-state-metrics`, `argocd`).
   - Then clone the repository on the VM: `git clone https://github.com/martinusboomuc/ai-infrastructure-lab.git`.
2. **Tailscale.** Join the tailnet as described in
   [network-topology.md](../network/network-topology.md).
3. **node_exporter.** Install it as described in the
   [monitoring README](../../infrastructure/homelab/monitoring/README.md).
4. **k3s.** Install it with the node configuration
   ([k3s README](../../infrastructure/homelab/k3s/README.md), "Cluster DNS"):

   ```bash
   sudo mkdir -p /etc/rancher/k3s
   sudo install -m 0644 ai-infrastructure-lab/infrastructure/homelab/k3s/node/config.yaml /etc/rancher/k3s/config.yaml
   sudo install -m 0644 ai-infrastructure-lab/infrastructure/homelab/k3s/node/resolv.conf /etc/rancher/k3s/resolv.conf
   curl -sfL https://get.k3s.io | sh -
   ```

5. **Namespaces and Secrets.** Create the `nexus` and `bankml` namespaces, then the four Secrets
   from the inventory, using the commands in the rotation sections above. Generate new values
   rather than recovering old ones:
   - a new `replay` pair in the Container App's API keys;
   - a new Tailscale client;
   - a new Grafana token.

   The storage connection string comes from Azure.
6. **Argo CD.** Bootstrap it with the three commands in the
   [k3s README](../../infrastructure/homelab/k3s/README.md), "Argo CD". It then syncs Nexus,
   BankML, kube-state-metrics, its own metrics NodePort and the NetworkPolicy Prometheus needs.
7. **Admin access.** Read the initial password on `k8s-01`, change it in the UI, then delete
   `argocd-initial-admin-secret`.
8. **Check.**
   - `sudo k3s kubectl -n argocd get applications` shows all five Synced and Healthy.
   - Prometheus targets `node-k8s-01`, `kube-state-metrics` and `argocd` are up.
   - `http://k8s-01/` shows the Nexus room with live presence.
   - A drift job created from the CronJob completes.

No data is lost with the VM. Prediction logs, drift history and the model registry are in Azure
and on `docker-01`; the cluster only runs jobs and the Nexus frontend.
